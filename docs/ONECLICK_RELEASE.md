## Protected database backup gate

The release path calls `scripts/zisu_release_backup_cli.py`, which reuses the WAL/DPAPI core in `scripts/qa_wal_backup_restore.py`. It refuses to proceed if ZISU is running, the DB/WAL/SHM/journal file set cannot be locked together for read-only access, the SQLite header or sidecars are unsupported, the protected vault is unavailable, or a later verification fails. The source DB is never opened by SQLite. A zero-source-write snapshot copies the DB and WAL while all present sidecar handles are held with Windows share-deny locks, rechecks source hashes and file-set presence, and omits SHM from the private snapshot. SQLite Backup API and restore checks run only on that snapshot. No `immutable=1` fallback is used.

After snapshot validation, SQLite Backup API creates an in-memory database. Integrity, foreign-key, schema-object, table-count, and logical-row checks run before serialization. The serialized image is protected with Windows DPAPI `CurrentUser`. A unique `.dpapi.partial` ciphertext file is written beneath `%LOCALAPPDATA%\ZisuReleaseBackupVault`; its ACL and contents are verified, then decrypted and restored in memory before atomic no-overwrite publication. WAL 2/2 to rollback 1/1 normalization is applied only to a private restore buffer. A helper failure cannot produce a successful backup report; an abrupt termination may leave an encrypted partial or an unreported final ciphertext, which must be reviewed separately. The private snapshot contains plaintext briefly on disk only inside the current-user-only ACL vault and is removed before ciphertext publication.

On the synthetic WAL fixture, read-only SQLite changed only the `-shm` entry: its `sha256` and `mtime_ns` changed; the DB and `-wal` entries did not.
