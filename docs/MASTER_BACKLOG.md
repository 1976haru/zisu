### V46-03 automatic report data-loss correction (2026-10-18)

- Current V46-03 estimate is **91%**; this latest state supersedes the older 87% table snapshot. The remaining gate is the user's normal desktop Chrome 5-cycle/report-path retest, not code/test coverage.
- Root cause in code: `_run_full_auto_test()` wrote worker-local `events` to the fixed `browser-verification-report.json`; `_write_interrupted_report()` separately wrote `self.events + _active_events`; `_save_report()` independently wrote only the GUI `self.events` and `_auto_summary`. All three writers targeted the same file without a shared run identity/serialization contract. Since the GUI queue transfers worker results asynchronously, a save/close before that handoff could make an empty or stale GUI snapshot the last writer. The supplied Windows JSON itself was not accessible here, so the precise triggering UI gesture is not asserted beyond this confirmed race.
- Fix: each automatic run now has a UUID `run_id` and dedicated JSON path. Each event/round carries the ID and is checkpointed through a serialized atomic writer; it flushes, replaces, reopens and compares persisted JSON with the in-memory payload. Final reports include requested/completed/success/failure/residual counts and verdict. Empty events are diagnostic, never PASS. GUI/manual save and close preserve a committed auto report; a late cancel cannot downgrade a final report.
- Regression: verifier + browser-manager suites **49 total: 48 PASS, 1 opt-in live-browser SKIP**. Covers 5/5 Mock success, 5/5 ordinary failures with continuation, failed-round continuation, cancellation, GUI-save/close with an empty GUI buffer, late-cancel protection, run-ID/readback equality, preflight failure counts and empty-report fail-closed behavior. `compileall`, GUI smoke, and `git diff --check` pass.
